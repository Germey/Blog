下面从零开始完成一次配置。

准备工作

开始前请确认：

  • 已注册并登录 Ace Data Cloud
  • 已创建或拥有一个可用应用
  • 本机已安装 Node.js 与 npm
  • 能够使用终端或 PowerShell
  • 准备使用 Codex CLI、Codex Desktop 或 VS Code 扩展中的至少一种

第一步：获取 Ace Data Cloud API Key

打开 Ace Data Cloud 应用列表，进入可用应用并复制 API Key。

请注意：

  • API Key 属于敏感凭证，不要写进公开仓库
  • 不要把真实 Key 放入教程截图
  • 建议按环境或用途分别创建和管理凭证
  • 怀疑泄露时，应及时轮换或撤销

本文统一使用环境变量 ACEDATACLOUD_API_KEY，避免将明文凭证直接写入 Codex 配置文件。

VS Code 配置要点

VS Code 扩展会读取同一份 ~/.codex/config.toml，但它能否看到 API Key 取决于扩展运行进程的环境。

配置后请完全退出并重新打开 VS Code。macOS / Linux 上，如果从图形界面启动后仍读取不到变量，可以从已经设置 Key 的终端运行：

使用以下环境时，应在扩展实际运行的一侧配置变量：

  • Remote SSH：远程主机
  • WSL：WSL Linux 环境
  • Dev Container：容器环境
  • Codespaces 或类似远程环境：对应远端会话

只在本机 Shell 设置变量，不能保证远程扩展自动获得它。

Codex Desktop 配置要点

Desktop 与 CLI 共享配置文件，但图形应用不一定继承终端里临时执行的 export。

如果 Desktop 读取不到 Key：

  1. 将环境变量设置为长期或系统级
  2. 完全退出 Desktop
  3. 重新启动应用
  4. 再检查 Provider 和模型

常见报错排查

1. 401、Unauthorized 或 Incorrect API Key

检查顺序：

  1. API Key 是否复制完整
  2. 环境变量名是否为 ACEDATACLOUD_API_KEY
  3. 当前进程是否在设置变量之后启动
  4. auth.command 是否符合当前操作系统
  5. 凭证是否仍有效

不要把完整 Key 输出到日志或聊天中。可以用仅判断“是否存在”的方式检查变量。

2. Provider 没有变成 acedatacloud

确认配置文件路径和 TOML 层级。常见错误包括：

  • 文件名写成 config.toml.txt
  • 编辑了另一个用户目录
  • 表名拼写不一致
  • 引号或数组格式错误
  • 保存后没有重启客户端

3. Base URL 请求失败

确认地址是：

不要漏掉 https:// 或末尾 /v1，也不要误用控制台页面地址。

4. CLI 能用，VS Code 不能用

这通常不是 Provider 配置问题，而是 VS Code 进程没有读取到环境变量。从已设置变量的终端启动 code .，或配置系统级变量后完全重启 VS Code。

5. WSL、SSH 或容器里读取不到 Key

环境变量需要设置在 Codex 或扩展真正运行的环境。Windows 主机上的 setx 不会自动写入 WSL；本机变量也不会自动传给远程 SSH 主机或容器。

6. 找不到想用的模型

不要手动猜测旧模型 ID。运行 /model 查看实时可选项，并检查应用权限、余额和当前 Provider。

7. 请求到达但无法完成复杂任务

先缩小任务范围：让 Codex只读分析、列计划，再逐步允许修改和测试。模型接入成功不代表所有仓库任务都应一次性完成；复杂变更仍需要明确的验收标准、测试和人工审查。

推荐的配置检查清单

在提交第一个正式任务前，逐项确认：

  • [ ] 已从应用列表获取有效 API Key
  • [ ] Key 保存在 ACEDATACLOUD_API_KEY
  • [ ] 没有把 Key 写入 Git 仓库
  • [ ] model_provider 为 acedatacloud
  • [ ] Base URL 为 https://api.acedata.cloud/v1
  • [ ] auth.command 与操作系统一致
  • [ ] 已完全重启 Codex 或 VS Code
  • [ ] /model 能看到 Provider 和模型
  • [ ] 最小测试请求成功
  • [ ] Usage History 中能看到对应调用记录

一个 Provider，减少重复配置

这套接入方式的重点并不是多写一段 TOML，而是建立稳定边界：

  • API Key 由环境变量管理
  • Provider 连接由 config.toml 管理
  • 模型在 Codex 内按任务选择
  • 调用记录和消耗在 Ace Data Cloud 控制台统一查看
  • CLI、Desktop 与 VS Code 共用一份配置

当认证、Provider 与模型选择被拆分清楚，许多“Codex 为什么又不能用”的问题就能快速定位，而不必反复登录、重装或复制多份配置。

打开 Codex 配置中心 查看不同客户端的官方指南，或前往 应用列表 获取 API Key。
